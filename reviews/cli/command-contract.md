# CLI 命令契约用例评审

评审范围：打包并隔离安装后的 `offckb` 命令入口、帮助、版本、JSON 输出和错误输出契约
源码版本：`develop@44ab81d`

## 接口说明

- 接口作用：为人工用户和自动化程序提供稳定、可判定的命令行入口。
- 输入：发布包中的 `offckb` 可执行程序、子命令、参数和全局 `--json`。
- 成功结果：进程以 0 退出；文本模式可读；JSON 模式的 stdout 只有一个命令结果。
- 失败结果：进程非零退出；JSON 模式的 stderr 给出单个结构化失败记录且 stdout 没有成功结果。
- 不负责：具体业务命令的链上语义、全屏 TUI 的显示和键盘交互。

## 待评审用例

| 用例 | 场景 | 预期结果 | 防止的问题 | 优先级 |
| --- | --- | --- | --- | --- |
| `CLI-01` | 从当前源码构建并隔离安装发布包后执行 `offckb --version` | 进程以 0 退出，输出版本与所安装发布包的 `package.json` 版本完全一致 | 发布包缺少可执行入口，或构建产物报告了错误版本 | P0 |
| `CLI-02` | 不带子命令启动 CLI，或显式请求顶层帮助 | 进程以 0 退出并显示顶层选项及核心命令；不创建 devnet、监听端口或启动后台进程 | 用户无法发现命令入口，或只查看帮助就产生运行时副作用 | P1 |
| `CLI-03` | 对具有专属结果对象的成功命令启用 `--json` | stdout 恰有一个可解析 JSON 对象，包含 `ok: true`、正确的 `command` 和命令结果；所有进度日志只出现在 stderr，且 stderr 每个非空行都是完整 JSON | 自动化需要从人类日志中抓结果，或 stdout 混入多条记录而无法稳定解析 | P0 |
| `CLI-04` | 将全局 `--json` 分别放在顶层命令前、命令后和嵌套子命令后 | 各位置都进入相同的 JSON 模式并执行相同命令，成功结果或失败结果的字段契约不随位置改变 | 脚本仅因全局参数位置不同就静默进入文本模式或调用错误命令 | P1 |
| `CLI-05` | 对没有专属结果对象的成功命令启用 `--json` | 进程以 0 退出，stdout 恰有一个包含 `ok: true`、正确 `command` 和 `completed: true` 的完成结果 | 部分成功命令没有机器可判定的完成信号 | P1 |
| `CLI-06` | 在 JSON 模式下分别提供缺失必填参数、未知选项和非法选项值 | 命令处理逻辑不执行，stdout 为空，进程非零退出；stderr 恰有一个 `ok: false` 失败记录，包含对应的参数解析错误码和清晰消息 | 非法输入仍产生业务副作用，或同一个错误被输出多次 | P0 |
| `CLI-07` | 命令语法有效，但执行阶段因缺少私钥或无效业务输入而失败 | stdout 不产生成功结果，进程以 1 退出；stderr 恰有一个 `code: COMMAND_FAILED` 的失败记录，且不包含内部堆栈或私钥内容 | 业务失败被误报为成功、无法区分解析失败与执行失败，或敏感信息泄漏 | P0 |

## 本轮需要确认

- 首期以 JSON 机器契约为主要门禁；默认文本模式只做帮助冒烟，不冻结具体排版和颜色。
- 请确认 `CLI-01` 至 `CLI-07` 是否构成首期 CLI 验收范围。
