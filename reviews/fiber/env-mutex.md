# Fiber 并发操作与环境互斥用例评审

评审范围：用户同时用两个终端操作同一个本地 Fiber 环境，或上次异常退出留下残留状态后再次操作时，OffCKB 如何判定环境是否可用、如何拒绝并发修改，以及如何区分"可以安全回收"和"仍被占用"。

版本依据：OffCKB `0.5.0-canary-ee0ad6b`（`ee0ad6b`），默认 CKB `0.208.0`、FNN `0.9.0`（`e6cb7ac`）。

## 接口说明

- 接口作用：OffCKB 在修改本地开发环境的命令执行期间独占该环境，避免两个进程同时改写同一份节点配置、运行记录或 FNN 数据；并判断上一次中断留下的锁、FNN 数据目录是否仍被占用。
- 输入：同一隔离用户目录中的两个并发或前后相接的命令。涉及入口包括 `node --fiber`、`fiber start`、`fiber stop`、`fiber clean`（含 `--data`）、`clean`（含 `-d`）。
- 成功结果：独占期间命令正常执行；环境中没有其他存活占用者时，操作继续并最终就绪或完成清理。
- 失败结果：环境正被另一个存活进程修改时，命令非零退出、stdout 为空、stderr 给出结构化失败，指出占用者及其用途，并且不产生任何本次操作的副作用。
- 不负责：不负责进程崩溃一致性、PID 复用、锁实现细节和 `lsof` 缺失时的平台矩阵；不负责 FNN 自身的通道状态恢复，也不负责跨机器或跨用户目录的并发。

## 待评审用例

| 用例 | 场景 | 预期结果 | 防止的问题 | 优先级 |
| --- | --- | --- | --- | --- |
| `FIB-LOCK-01` | - [x] 用户在一个终端启动 Fiber 环境（该操作正在修改环境）时，在第二个终端对同一环境执行另一个会修改环境的命令，例如 `fiber start`、`node --fiber` 或 `fiber clean --yes` | 第二个命令非零退出，stdout 为空，stderr 给出结构化失败并说明环境已在使用中：或指出另一个 OffCKB 进程正在修改该环境及其用途，或指出受保护的 Fiber daemon 已在运行，并引导用户等待或先停止；先发起的命令不受影响，环境按原预期就绪并可开通道支付；第二个命令不占用节点端口、不改写节点清单与配置，环境恢复空闲后重试成功 | 两个进程同时改写同一份配置或数据，或后发起者被误判成功、抢占甚至终止先发起的服务 | P1 |
| `FIB-LOCK-02` | - [x] 用户上一次运行被强制中断，环境中留下指向已退出进程的锁文件；随后用户在同一环境正常执行 `fiber start` 或 `node --fiber` | OffCKB 识别该锁的持有者已不存在，自动回收后继续启动，命令以 0 退出且环境完整就绪并自动互联，随后的停止或清理不再被该残留锁阻塞；恢复过程不删除任何仍被存活进程持有的锁，也不改动节点身份、账户与已有链数据 | 残留锁让用户永久无法启动，只能手工删文件；或为了清理而误删仍被其他进程持有的锁，使并发保护失效 | P1 |
| `FIB-LOCK-03` | - [x] FNN 数据目录的数据库锁文件仍被一个存活进程持有（例如上次异常退出后残留的 FNN 现场），用户执行 `fiber clean --data --yes` 或 `fiber clean --yes` | 命令非零退出并说明无法确认 Fiber store 已关闭、当前存在被持有或无法判定的锁，提示先停止所有 FNN 进程后重试；本次不删除 FNN 数据、身份密钥和配置，不报告清理完成；用户释放占用后重试，清理按所选范围正常完成 | 清理误删仍被写入的数据库导致数据损坏，或无法判定占用时按"未占用"猜测，造成身份与通道记录丢失 | P1 |

## 判定与范围边界

- 环境锁的有效期是"操作进行期间"：启动完成、清理完成或命令失败后即释放，因此判定不能依赖"启动后仍存在某个锁记录"；残留锁场景以"启动成功、环境可用、后继命令不再被阻塞"为准。
- 并发场景使用同一个隔离用户目录内的两个真实进程，并等确认环境已被正在运行的命令预留后再发起第二个命令，避免两个进程同时起跑的竞态。第二个命令的失败以退出码、stdout 为空和结构化错误共同判定，不能只凭日志文本；拒绝原因只接受两条环境保护分支：环境被另一个 OffCKB 进程占用，或受保护的 Fiber daemon 已在运行；其他形式的失败不算通过。先发起的一方通过进程集合、节点清单、端口占用和一次真实支付证明未被影响。
- 残留锁场景只需证明"锁的持有者已不存在时操作继续，且不抢占存活占用者的锁"；锁文件的格式、字段和实现细节不作为判定对象，也不要求用户手工维护。
- 数据目录占用场景只验证"存在被持有或无法判定的锁时拒绝清理"；不覆盖锁缺失、`lsof` 不可用等平台差异，也不扩展为数据库损坏修复。占用由测试在同一隔离环境内自行构造，不读取或影响开发者真实环境。
- 与既有用例的分工：[停止、重启与清理](lifecycle-state.md) 覆盖用户主动停止、重启与各类清理范围，[启动失败与恢复](startup-recovery.md) 覆盖错误路径、端口占用和余额不足后的修正重试；本文件只覆盖"同一环境被并发修改或被残留占用"这一类的判定与拒绝。
